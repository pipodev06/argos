# Roles de BD: migrador vs runtime (2026-09-25, plan P0 D4)

**Problema:** el server migraba y operaba con un solo rol (dueño de todo): quien comprometiera el proceso podía `DROP TRIGGER audit_log_guard` y reescribir la auditoría.

**Decisión (modo de dos roles, opcional; el de un solo rol sigue funcionando para desarrollo y tests):**
- `argos_owner` (dueño del esquema; solo migra) y `argos_app` (runtime). El dueño es miembro del rol de runtime (`GRANT argos_app TO argos_owner`) para poder cederle tablas y seguir migrándolas.
- `argos-server migrate` (sin leer el resto de la config): usa `ARGOS_MIGRATE_DATABASE_URL` (o `DATABASE_URL`), aplica las migraciones y, con `ARGOS_APP_ROLE`, llama a `store.PrepareRuntimeRole` (idempotente): DML en todas las tablas, `USAGE` en secuencias, `ALTER DEFAULT PRIVILEGES` para lo que creen migraciones futuras, sin `UPDATE` sobre `audit_log`, y cede al runtime la propiedad de las tablas particionadas (`metrics`, `service_checks`, `disk_samples`) y sus particiones, con `CREATE` en `public`.
- `ARGOS_AUTO_MIGRATE=false` (default `true`): el server no migra; se niega a arrancar si `store.SchemaPending` (goose `HasPending`) dice que hay migraciones pendientes.
- Deploy: `install-server.sh --create-local-db` crea ambos roles con claves aleatorias; la clave del dueño vive en `/etc/argos/argos-migrate.env` (0600 root) y solo la lee `argos-admin migrate` (el server en marcha nunca la tiene).

**Por qué el runtime es dueño de las particionadas:** el mantenimiento hace `ATTACH`/`DETACH PARTITION`, que exigen ser dueño, y `DETACH ... CONCURRENTLY` no puede ir dentro de una función `SECURITY DEFINER` (no corre dentro de una transacción). Alternativa descartada: `DETACH` no concurrente en función (bloqueo `ACCESS EXCLUSIVE` sobre el ingest). Límite aceptado: un runtime comprometido puede destruir series de tiempo y crear objetos en `public`, pero **no** tocar `audit_log` (ni su trigger), `users`, `sessions` ni ninguna otra tabla más allá de DML.

**Verificado:** `retention/roles_test.go` (Postgres real: como runtime, 11 sentencias DDL/trigger/UPDATE/DELETE de auditoría fallan con `42501`; el mantenimiento completo corre y borra la partición legacy; el dueño aún puede alterar las particionadas; idempotencia; nombre de rol inválido; miembro requerido) y prueba de humo con una copia restaurada de la BD real (migrar como dueño, `create-admin` y ~20 endpoints como runtime, workers 30 s sin un solo error de permisos). **No verificado:** el instalador en un Linux real.

**Pendiente/deuda:** los tests de `store` y `httpapi` siguen corriendo con un solo rol (truncan y recrean el esquema); la cobertura del modo dividido es el test de retención y la prueba de humo. Una migración futura que cree otra tabla particionada debe cederse al runtime: `PrepareRuntimeRole` ya lo hace en cada `migrate`.
