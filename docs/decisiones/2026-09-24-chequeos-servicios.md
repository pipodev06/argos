# Chequeos de servicios (2026-09-24): diseño aprobado y tanda 1 (servidor + agente) implementada y probada
Decisiones del usuario: los chequeos los ejecuta SOLO el agente (sondas del server = fase 2); destinos por defecto solo el propio equipo (loopback + IPs propias; otro destino exige `ARGOS_CHECK_ALLOW` local que el server no puede ampliar); tokens prohibidos en la URL, van en un campo secreto cifrado (mismo `secretbox`/`ARGOS_SECRET_KEY` que los canales; la API nunca lo devuelve); muestreo de latencia cada 15 min; transiciones 180 d; alertas con `kind='service_check'`. Excepción documentada: `tls_cert` hace solo el handshake y lee `NotAfter` (con `InsecureSkipVerify` únicamente en ese tipo).
Tipos: `tcp`, `http` (GET, sin redirects, `expect_status`, `expect_text` 64 KiB solo booleano), `tls_cert` (días), `service` (Windows con `SC_MANAGER_CONNECT`+`SERVICE_QUERY_STATUS`; Linux `systemctl show -p LoadState -p ActiveState -p SubState --`; otros `unknown`). Límites del agente: ≤20 chequeos, intervalo ≥30 s, concurrencia ≤4, respuesta ≤64 KiB, timeout ≤10 s.
Servidor: migración 00017 (`service_check_defs`, `service_check_state`, `service_check_events`, `service_checks.check_id/value`, kind `service_check` en reglas y `alert_candidates`); API `/service-checks` (CRUD; viewer sin `header_name` ni query de la URL), `GET /hosts/{id}/service-checks` y `/{check_id}/events`; entrega en la respuesta al reporte (`checks_rev`; `data.checks={rev,items}`, tope 50/~15 KiB); resultados en `services[]` (`check_id,status,response_ms,value,detail,ts`; `detail` de catálogo fijo); `ARGOS_SERVICE_EVENTS_RETENTION_DAYS` 180. Decisiones menores: `warn_or_down` en reglas; el primer resultado registra un evento con `from_status` NULL; se rechaza una URL cuya query parezca credencial; si un secreto no descifra, el chequeo se omite de la entrega; agente: cruzar un umbral da `warn`/`down` con `detail=ok`, `tls_cert` manda `trusted` extra, servicio detenido = `down`/`status_mismatch`.
QA real contra la BD (agente nuevo): tcp a Postgres `up` 18 ms; servicio de Windows `postgresql-x64-18` `up`; puerto cerrado `down`/`refused`; destino 10.255.255.1 `unknown`/`blocked` (política local); HTTP a `127.0.0.1:5173` `down` porque Vite solo escucha en `::1` y `localhost` da `up`; token en la query rechazado (400); alerta `service_check` abre en ~30 s y resuelve `recovered`; secreto no sale por API ni auditoría y está cifrado en BD (45 bytes, sin texto plano). Datos de prueba borrados.
Pendiente: pantallas (tanda 3), sondas del server (fase 2), systemd sin privilegios y macOS sin probar, `-race`; deuda: `service_checks` sin FK a la definición (se limpia por retención); `peak_value` de `tls_cert` usa GREATEST.
