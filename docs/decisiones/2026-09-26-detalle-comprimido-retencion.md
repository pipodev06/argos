# Detalle comprimido por host y día + retención por host/grupo/global (2026-09-26)

**Motivo:** el usuario hospeda argos (clientes con suscripción de 30 o 90+ días de detalle) y quería (1) menos disco y (2) retención distinta por cliente sin reiniciar. Se descartó TimescaleDB (compresión bajo Timescale License: restringe ofrecerlo como servicio; extensión con reinicio y superusuario; no existe en Postgres administrados) y Btrfs (no se acumula con datos ya comprimidos; CoW y `nodatacow` desactiva la compresión). Se eligió empaquetado propio.

**Medición:** métricas reales de `root_home` (30 s): fila actual 178 B con índice; formato propio **7,77 B/muestra (22,9× menos)**, ~23 KB por host-día. 1000 hosts × 365 d a detalle completo ≈ 8,5 GB (antes ≈ 187 GB). El test del códec falla si pasa de 12 B/muestra (fixture real recortado en `server/internal/chunk/testdata/`).

## Diseño (migración 00033)
- Tabla caliente `metrics` (particiones diarias) sin cambios, con vida útil = **ventana caliente** `ARGOS_METRICS_HOT_DAYS` (8, mínimo 8: el rollup lo exige y el server rechaza reportes de >7 días, así que no llegan datos tardíos a una partición ya empaquetada). `ARGOS_METRICS_RETENTION_DAYS` pasa a ser el **default global de retención de detalle** (30).
- `metrics_chunks(host_id, day, n, codec, data bytea, packed_at)`: una fila por host y día, formato columnar propio (`server/internal/chunk`: delta-de-delta de ts, delta + zigzag + varint por columna, mapa de presencia para NULL, `compress/flate` nivel 9, CRC32; lossless salvo el redondeo de flotantes a 2 decimales; el decodificador acota la descompresión; fuzz de ida y vuelta).
- **Empaquetador** (`retention/pack.go`): antes de borrar una partición diaria ya resumida, empaqueta cada host, verifica decodificando y solo entonces permite el DROP. 1 partición con trabajo por ciclo (`packBudget`); "empaquetado" = `n` del chunk igual a las filas crudas. Un chunk que falla siempre deja la partición sin borrar y loguea ERROR cada ciclo. Backfill natural: las particiones de 8–30 días existentes se empaquetan y liberan disco.
- **Retención efectiva = host ?? grupo ?? global**, 8..730 días (`hosts.detail_retention_days`, `host_groups.detail_retention_days`, `settings.metrics_detail_days`). `retention/trim.go` recorta chunks vencidos **en cada ciclo** (sin escribir si no hay vencidos): los cambios rigen al siguiente ciclo, sin reiniciar. Subir vale hacia adelante; bajar recorta.
- Lectura: `Store.DetailRange(ctx, host, from, to, fn)` mezcla chunks y filas crudas en orden sin cargar todo; `Store.EffectiveDetailDays`. Aún no expuestos por HTTP.
- API (solo admin, auditada): `GET/PUT /api/v1/settings/retention`; `PATCH /api/v1/groups/{id}` y el endpoint de retención de host aceptan `detail_retention_days` (null = heredar); detalle de host y de grupo devuelven propio y efectivo. Reducir exige `confirm_shrink=true` (409 `shrink_needs_confirm` con `days_lost/chunks/est_bytes` si se perderían datos; `EstChunkBytes` = 23 KB por host-día).
